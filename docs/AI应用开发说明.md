# AI 电商客服：业务与技术说明

目标岗位为 AI 应用开发。项目展示的是将模型输出转化为受业务规则约束的服务流程：查询事实、检索政策、提议操作、用户确认、人工接管、结果回查。

## 技术栈与职责

| 技术 | 本项目职责 | 可核验位置 |
| --- | --- | --- |
| Next.js 16 / React 19 / TypeScript | 三栏客服工作区、客户上下文、增量对话、操作确认与人工处理 | frontend/app、frontend/lib |
| FastAPI / Pydantic | HTTP/SSE、身份与角色权限、工具参数 schema | backend/app/main.py、routers/、models/schemas.py |
| LangGraph | 有界模型与工具循环、真实节点事件、上下文与工具结果反馈 | agents/graph.py |
| 中文多粒度 BM25 | 商品说明和政策的 RAG 检索基线与来源展示 | knowledge_base/retriever.py |
| MySQL / InnoDB | 客户、订单、会话、工单、业务状态与审计记录的主数据库 | db.py、commerce.py、service.py |
| SQLAlchemy Core / PyMySQL | 参数绑定、连接池、事务、MySQL 驱动；兼容隔离 SQLite 测试 | db.py |
| unittest / Playwright | 并发与业务权限回归、浏览器跨角色协作及移动布局检查 | backend/tests、frontend/tests |

不引入 Redis、消息队列、微服务或多智能体来替代本项目已有的单库事务。未实施向量检索、重排、模型微调、真实 ERP 接口或生产多租户；不能在简历中声称具备这些实现。

## 企业业务映射

- CRM 服务侧：查看客户订单和咨询历史，关联工单与对话；工单有负责人、演示处理时限和处理事件。
- 订单履约侧：库存预留、订单状态、模拟发货/运输/送达节点、预计补货日期。职责接近轻量 OMS 与库存模块，不能等同于完整 ERP。
- 人工协作：系统从最近对话和实际工具记录生成可核对的交接摘要；这不是模型生成摘要。接管期间客户消息发给人工队列，AI 入口由服务端拒绝，未执行的 AI 提议失效；完成后恢复 AI。
- 业务边界：所有物流、支付与换货处理结果都是演示。客服不能承诺已真实退款或真实换货。

## 管理员 AI 运营

管理员通过 AI 入口调用 `propose_create_product` / `propose_update_product` / `propose_product_listing`，使用 `query_admin_products` 查询含已下架商品的目录。买家的模型工具列表不包含这些管理工具，执行端仍检查管理员权限，确认时再次检查身份和操作归属。商品数据始终通过 Pydantic 校验，价格用整数分。

工具先保存待确认草稿与商品快照，页面展示新增字段或修改前后值。确认事务锁定商品行并比对快照；下单导致库存变化、手工调价或补货变更后，旧预览返回 409，重新生成后才能确认。手动写入与 AI 写入复用 `catalog.py`，成功时同事务保存修改前后数据、操作者及 AI action 编号；新增商品重复编号由主键约束拒绝。历史订单使用成交快照。下架不删除商品，只阻止买家展示和新购买；管理员可继续编辑或重新上架。购物车保留已下架项并提示移除，结算服务再次拒绝；已有订单继续履约。库存增减在提议事务锁定商品后计算绝对值，再保存快照供确认。

这是单店管理功能，尚未实现发布审批、仓库入库和库存流水核算。规则模式提供明确格式的流程演示；新增管理工具的真实模型效果仍需单独评测。

## MySQL 事务设计

1. 购物车与下单先锁定当前客户行，串行处理同一客户的购物车变更及重复提交。下单按商品编号顺序锁定购物车内商品，再读取价格及上下架状态；库存更新使用 `active=1 AND stock >= quantity` 条件，防止两个客户争抢最后一件商品时超卖。
2. 取消、支付、发货与收货在事务中锁订单；取消重复执行不重复回补库存。
3. 确认操作先锁会话，再锁待确认记录；有效期、所属客户与最新订单状态重新校验。操作结果与状态在同一事务写入。
4. 人工接管及工单处理遵循“会话 → 工单”的锁顺序，避免客户补充消息与人工回复采用相反锁顺序。
5. MySQL 使用 READ COMMITTED。订单幂等由 `(user_id, request_key)` 唯一约束保护；未完成售后工单通过生成列与唯一索引防止重复。
6. SQLAlchemy 启用连接池与 `pool_pre_ping`，隐藏日志中的 SQL 参数。SQLite 仅作为隔离测试/迁移来源，不能用其测试通过替代 MySQL 验证。

当前初始化支持建表、索引和版本记录，新功能采用新增关联表保存详情，兼容原始数据。不是完整的 Alembic 迁移体系；未来改变已有 MySQL 列结构时，需要显式版本迁移和回滚策略。

参考：[SQLAlchemy MySQL 文档](https://docs.sqlalchemy.org/en/20/dialects/mysql.html)、[MySQL 锁定读](https://dev.mysql.com/doc/refman/8.0/en/innodb-locking-reads.html)。

## 五分钟演示路线

1. 买家登录，咨询“查询我的订单和物流”，展示数据库事实、资料来源和实际工具执行。
2. 咨询“订单 ORD-DEMO 的耳机左侧无法连接，帮我申请售后”，确认卡片后创建工单。
3. 点击转人工并关联 ORD-DEMO，沿用同一工单；管理员在另一标签页接单，查看客户档案和交接摘要。
4. 客户补充排查结果，人工回复并填写“模拟换货”的处理结果。买家刷新查看，结单后继续查询售后进度。
5. 管理员查看按规则/LLM 分开统计的首次文本响应、总耗时、工具执行与 Token。演示跨客户查单被拒绝及未确认写操作不执行。

## 评测与证据

- `backend/evaluation/report.json`：相同语料与标注的旧检索 / BM25 对比，29 条人工样例。只能讨论检索表现。
- `backend/evaluation/service-report.json`：规则模式的服务流程契约回归，覆盖人工闭环、越权、忙碌状态、确认幂等、履约与观测。不能解释为真实模型任务完成率。
- `backend/scripts/smoke_llm.py`：可选真实模型工具链检查，使用虚构数据且可能产生调用费用，本次不自动运行。
- `logs/mysql-tests.log`：本机 MySQL 业务回归；浏览器检查与截图保存于 `logs/`，不提交运行数据。
- 运行观测中的“执行完成”只代表程序没有报错；p50/p95 取当前最近 100 条记录内选定模式的完成运行，不能代表生产 SLA。

后续优先级：扩充脱敏真实语料与独立保留测试集；对比向量与混合召回；加入真实模型的工具/参数、引用一致性和多轮任务完成评测；再按实际负载考虑缓存、后台任务及跨实例恢复。
